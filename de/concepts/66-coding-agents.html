66 · Coding Agents

Erklär es einem 12-Jährigen Stell dir eine Helferin vor, die deinen Code lesen, ausführen und reparieren kann — aber statt zu raten prüft sie ihre eigene Arbeit. Sie macht eine Änderung, führt die Tests aus, sieht, dass einer scheitert, liest warum, behebt es und führt erneut aus — bis alle Tests bestehen. Das ist ein Coding-Agent: eine KI, die Code schreibt, testet und repariert, in einer Schleife, mit den Testergebnissen als Wahrheit darüber, ob es richtig ist.

Intuition

Ein Coding-Agent ist ein Agent-Loop (23), spezialisiert auf Software: Statt generischer Tools bekommt er Code-Tools — Datei lesen, Codebasis durchsuchen, Tests ausführen, Datei bearbeiten — und statt eine Frage zu beantworten, erzeugt er eine funktionierende Änderung. Der Loop ist: planen → handeln (lesen/suchen/ bearbeiten/ausführen) → beobachten (Testausgabe) → anpassen → wiederholen, bis die Aufgabe fertig ist. Der entscheidende Unterschied zu einer reinen Chat-Antwort: Der Agent kann seine eigene Ausgabe verifizieren, indem er sie ausführt.

Was passiert technisch

Ein Coding-Agent (Claude Code, Codex, Cursors Agent-Modus) ist ein Modell in einem Harness, der code-spezifische Tools (21) bereitstellt und ein Arbeitsverzeichnis verwaltet. Jede Loop-Iteration sieht so aus:

1. Planen:  "dem CLI ein --json-Flag hinzufügen"
2. Handeln: read_file("cli.py")   → aktuelle Struktur verstehen
3. Handeln: grep("--json")        → prüfen, dass nichts existiert
4. Handeln: edit("cli.py", ...)   → die Änderung schreiben
5. Handeln: run("pytest")         → die Testausgabe beobachten
6. Beobachten: ein Test scheitert → Fehler lesen, fixen, erneut ausführen
7. Wiederholen bis alle Tests bestehen → fertig

Drei Ideen machen das funktionieren:

  • Der Test-Harness ist die Ground Truth (44): Der Agent vertraut nicht seinem eigenen Urteil „sieht richtig aus“ — er führt die Tests aus und liest das Urteil. Die Tests entscheiden, ob die Arbeit fertig ist.
  • Self-Healing: ausführen → Scheitern sehen → Fehler lesen → fixen → erneut ausführen. Die Fehlermeldung ist Feedback, keine Sackgasse. Die meisten Coding-Agents verbringen die meiste Zeit in diesem Fix-Loop, nicht beim ersten Schreiben.
  • REPL-getriebene Entwicklung: Der Agent führt ein Snippet aus, liest die Ausgabe und iteriert — eine dialogische Version des klassischen Read–Eval–Print-Loops. Schnelle Experimente gegen den laufenden Code ersetzen lange Denkstrecken.

Im Hintergrund ist jeder Tool-Aufruf ein Funktionsaufruf (27), den das Modell auswählt; der Harness führt ihn aus, fängt stdout/Exit-Codes ab und gibt das Ergebnis als nächste Beobachtung zurück. Das Modell führt selbst nie Code aus — der Harness tut das, und das Modell liest nur das Transkript (21).

Warum es mir (als Code-Nutzer) weiterhilft

  • Das ist ein großer Praxis-Use-Case: Coding-Agents sind heute die am weitesten verbreitete Form von Agenten. Den Loop zu verstehen heißt zu verstehen, was der Hype tatsächlich unter der Haube tut.
  • Du steuerst einen Loop, keine Magie: Für gute Ergebnisse gibst du dem Agent eine klare Aufgabe, einen Test zum Erfüllen und lässt ihn iterieren. Du „redest nicht mit einem Programmierer“ — du steuerst eine Schleife.
  • Du weißt, was du prüfen musst: Weil der Test-Harness die Ground Truth ist, bestimmt die Qualität deiner Tests die Qualität der Agentenarbeit. Schwache Tests → selbstbewusst falscher Code. Das erhöht den Wert guter Tests.
  • Du kannst es debuggen: Wenn ein Coding-Agent scheitert, liegt der Fehler im Loop — ein falscher Tool-Aufruf, ein nicht existierender Test, eine Änderung, die nicht gelandet ist. Wer das Muster kennt (23, 21), findet das schwache Glied, statt nur auf die Ausgabe zu starren.
  • Architektur-Bewusstsein: Ob er replant, wie viel Kontext er hält und welchen Tools er vertraut, sind dieselben Design-Entscheidungen wie bei jedem Agenten (60) — jetzt kannst du Tools danach beurteilen.
