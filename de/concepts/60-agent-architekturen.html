60 · Agent-Architekturen

Erklär es einem 12-Jährigen Zwei Arten, eine große Hausaufgabe anzugehen: Der Impulsive macht einen Schritt, schaut was rauskam, macht den nächsten — und bessert unterwegs nach. Der Planer schreibt erst die ganze Gliederung auf und arbeitet sie dann ab. Beide kommen ans Ziel, aber je nach Aufgabe ist mal der eine, mal der andere schneller und sorgfältiger. Genau so sind ReAct und Plan-and-Execute gebaut.

Intuition

Ein Agent (09) ist ein Loop: Denken → Handeln → Beobachten. Aber wie man diesen Loop strukturiert, ist eine Design-Entscheidung mit echten Folgen für Kosten, Robustheit und Fehleranfälligkeit. Die zwei Grundmuster sind ReAct und Plan-and-Execute; alles Weitere (Multi-Agent, Orchestrator) baut darauf auf.

ReAct: Denken → Handeln → Beobachten

ReAct (Reason + Act) lässt das Modell in jedem Schritt abwechselnd überlegen („Thought“), ein Tool aufrufen („Action“) und das Ergebnis lesen („Observation“) — bis es die finale Antwort hat. Kein fester Plan; die Strategie entsteht Schritt für Schritt aus den Beobachtungen.

Schritt 1: Thought "Ich brauche zuerst den Preis von X"
          Action: search("Preis X")   Observation: "12 €"
Schritt 2: Thought "Jetzt vergleichen mit Y"
          Action: search("Preis Y")   Observation: "9 €"
Schritt 3: Thought "Ich habe genug" → Antwort

Plan-and-Execute: erst Plan, dann Schritte

Hier erzeugt das Modell zuerst einen kompletten Plan („1. recherchieren, 2. berechnen, 3. schreiben“), und ein Ausführer arbeitet die Schritte ab — idealerweise ohne dass der Planer jeden Zwischenschritt erneut sehen muss. Bei Überraschungen wird replant.

ReActPlan-and-Execute
Vorgehenjeder Schritt einzeln, adaptivkompletter Plan vorab
Modell-Aufrufeviele (pro Schritt einer)wenige (Plan + Ausführung)
Kosten/Latenzhöherniedriger bei langen Tasks
Fehlerverhaltenkurs-korrigiert gut, verliert aber Ziel/Fadenbleibt am Ziel, aber Plan kann falsch sein

Faustregel: unklar was zu tun ist → ReAct; klar was zu tun ist, aber lang → Plan-and-Execute.

flowchart TD T[Task] --> R{Architektur} R -->|ReAct| L1[Durchlauf: Thought] --> L2[Action] --> L3[Observation] --> L4{fertig?} L4 -->|nein| L1 L4 -->|ja| D1[Antwort] R -->|Plan & Execute| P1[Planner: kompletter Plan] --> W1[Worker führt Schritt 1..n aus] --> P2{Plan noch gültig?} P2 -->|Überraschung| P1 P2 -->|ok| D2[Ergebnis]

Beide Architekturen enden im selben Loop-Grundgerüst (35) — sie unterscheiden nur, wann geplant wird.

Multi-Agent-Patterns kurz: Orchestrator/Worker

Statt einem Alleskönner-Agent teilt ein Orchestrator den Task an spezialisierte Worker (39) auf: „du recherchierst, du implementierst, du testest“, fasst zusammen und entscheidet. Vorteile: kleinere Kontexte pro Agent, parallele Ausführung, klare Verantwortlichkeiten. Nachteil: Koordinations-Overhead, Fehler können sich zwischen Agents verstecken. Für kleine Tasks bleibt ein einzelner Agent fast immer einfacher und billiger.

Frameworks — neutral betrachtet

Alle Frameworks kochen dieselbe Suppe: der Agent-Loop (09/35) plus Zustandsverwaltung plus Tool-Registry.

FrameworkSchwerpunktTypischer Kompromiss
LangGraphAgent-Abläufe als expliziter Graph (Zustand, Verzweigungen, Loops)mehr Boilerplate, volle Kontrolle
CrewAIRollenbasierte Teams („Researcher“, „Writer“) mit Aufgabenschnell startbar, weniger Kontrolle über den Ablauf
Claude Code / Agent SDKfertiger Coding-Agent bzw. SDK um denselben Harnessopinionated, stark für Code-Tasks

Wichtig: kein Framework ersetzt das Verstehen des Loops. Wer weiß, wie ReAct funktioniert, kann jeden davon notfalls in ~100 Zeilen selbst schreiben.

Agent-Eval: wie misst man, ob ein Agent gut ist?

  • Task-Success-Rate: Anteil gelöster Tasks über einen Satz von Testfällen — die Kernmetrik. Braucht definiertes „gelöst“ (Tests bestehen, Datei korrekt …).
  • Steps & Kosten: wie viele Modell-Aufrufe/Tools/Tokens bis zum Erfolg? Ein Agent mit gleicher Quote aber halben Kosten ist besser.
  • Trajectory-Eval: war der Weg sinnvoll? (unnötige Umwege, gelöschte und neu angelegte Dateien, Halluzinations-Tool-Calls). Manuell oder per LLM-as-Judge über den Verlauf.
  • Verwandt: klassische Metriken (15), aber auf Task-Ebene statt Token-Ebene; Robustheit gegen Prompt-Injection (26) gehört ebenfalls aufs Blatt.

Warum es mir weiterhilft

  • Bewusste Wahl statt Default: ich kann entscheiden, ob mein Use-Case ReAct-, Plan- oder Multi-Agent-Profil braucht.
  • Kostenkontrolle: Plan-and-Execute spart bei langen Tasks echte Modell-Aufrufe.
  • Messbarkeit: ohne Success-Rate + Kosten pro Task ist Agent-Bau nur Vibes.
  • Framework-Unabhängigkeit: die Muster wechseln mit; der Loop bleibt.
