40 · Sandboxing & Härtung

Erklär es einem 12-Jährigen Gefährliche Experimente macht man im Spielplatz, nicht im Wohnzimmer. Sandboxing heißt: Code, dem man nicht traut, läuft isoliert — damit ein Fehler nicht das ganze System kaputt macht.

Intuition

Ein Agent führt Code aus, den er (oder ein Modell) geschrieben hat — oft unzuverlässig oder böswillig. Damit ein Fehler oder Angriff keinen Schaden anrichtet, läuft solche Ausführung in einer Sandbox: einem isolierten Bereich mit begrenzten Rechten, Dateien und Netzwerkzugang.

Was passiert technisch

1) Risiko-Stufen (Least Privilege)

  • Read-only: lesen/greppen — kein Schreibrecht, kaum Risiko.
  • Writable-Root: schreiben nur in erlaubte Verzeichnisse (writable_roots).
  • Irreversibel: löschen/force-push/Deploy — immer menschliche Bestätigung.

2) Isolationsebenen

  • Leicht (bwrap/Landlock/seccomp): Namespace-/Syscall-Isolation, ~0 Overhead — gut für read-only und kleine Builds.
  • Mittel (Docker-rootless/Podman): Container mit read-only rootfs, non-root User, kein docker.sock — gut für Builds/Ausführung.
  • Schwer (gVisor/MicroVM): eigener Kernel — nur für hoch-vertraulichen Code.

3) Netzwerk & Credentials

Outbound per Allowlist (nur erlaubte Domains, besser: SNI-Filter am Proxy); Credentials nie im Sandbox-Kontext (z.B. Git-Token nur beim Clone injiziert). Wichtig: Netzwerk- UND Dateisystem-Isolation immer zusammen — sonst exfiltriert ein kompromittierter Prozess Secrets.

Warum es mir (als Code-Nutzer) weiterhilft

  • Du kannst Agenten autonom Code ausführen lassen, ohne den Rechner zu riskieren.
  • Du verstehst den Security-Blaster-Radius: Sandbox pro Sitzung = ein Fehler trifft nur diese Sitzung.
  • „Fail closed“: Wenn die Sandbox nicht startet, hart abbrechen — nie ungeschützt laufen.
