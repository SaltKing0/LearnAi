41 · MCP (Model Context Protocol)

Erklär es einem 12-Jährigen Bisher musste für jede Verbindung Modell↔Werkzeug ein eigenes Kabel gelötet werden: 10 Tools = 10 verschiedene Stecker. MCP ist wie USB-C für KI — ein Standard-Stecker. Wer ein Tool einmal als MCP-Server anbietet, kann es mit jedem MCP-fähigen Modell/Client benutzen. Und umgekehrt: ein Client versteht automatisch alle MCP-Server.

Was ist MCP?

Ein offener Standard (von Anthropic, Ende 2024) für die Verbindung zwischen KI-Anwendungen und externen Kontext: Werkzeuge, Daten, Prompts. Vor MCP baute jede App ihre eigenen Function-Calling-Integrationen (Konzept 29) — MCP vereinheitlicht das in ein Client-Server-Protokoll.

flowchart LR A[Host · z.B. Claude Desktop, IDE] -->|MCP-Client| S1[Server: Dateien] A -->|MCP-Client| S2[Server: GitHub] A -->|MCP-Client| S3[Server: DB] S1 --- T1[Tools · Resources · Prompts] S2 --- T2[Tools · Resources · Prompts] S3 --- T3[Tools · Resources · Prompts]

Ein Host kann mehrere MCP-Server parallel anbinden — jeder Server stellt Tools, Resources und Prompt-Vorlagen bereit.

Die drei Server-Primitiven

  • Tools — Funktionen, die das Modell aufrufen darf („Datei lesen“, „PR erstellen“). Das ist das MCP-Pendant zu Function Calling.
  • Resources — Daten, die der Client lesen/anhängen kann (Dateien, DB-Zeilen). Kontext, keine Aktionen.
  • Prompts — vorgefertigte Prompt-Vorlagen, die der Server anbietet (z.B. „Code-Review dieses PRs“).

Warum das für dich als Code-Nutzer zentral ist

  • Einmal bauen, überall nutzen: dein MCP-Server funktioniert in Claude Desktop, IDEs, Agent-Frameworks — ohne pro App nachzubauen.
  • Weniger Kleber-Code: statt 20 handgeschriebener Function-Definitionen konsumierst du fertige Server (GitHub, Slack, Postgres …).
  • Aber: MCP löst nicht die Sicherheitsfragen — Prompt Injection über Tool-Ergebnisse (Konzept 26) und Sandboxing (Konzept 40) bleiben deine Verantwortung.
