48 · Retrieval Fine-Tuning

Explain it to a 12-year-old Imagine searching a library for the one chapter that answers your question. If everything is bound into giant tomes, you can't find anything precise; if it's all torn into tiny scraps, you lose the context. RAG has exactly the same problem: how you cut up documents, search them, and re-sort the best hits decides whether the answer is good or garbage.

Intuition

RAG (08) isn't a switch, it's a loop with many tuning knobs. Most "RAG doesn't work for us" cases aren't model problems but retrieval problems: the right text wasn't retrieved, was chopped up, or got crowded out by fifteen mediocre hits. This concept is the toolbox for exactly those knobs.

Chunking: why chunk size determines answer quality

A chunk is the smallest unit that gets stored and found. Too big: the embedding vector averages over many topics → imprecise similarity, and one hit eats half your context window. Too small: the sentence "therefore it also applies retroactively" lands in the index without its reference sentence → the content is there, but incomprehensible.

Attaching metadata (source, date, chapter, department) to every chunk almost always pays off: it lets you filter ("manual 2024 only"), cite, and suppress duplicates. Overlap prevents a sentence sitting exactly on the boundary between two chunks from losing its neighbors.

Hybrid search: BM25 + vectors

Vector search (30) understands meaning but fails on exact tokens: error codes ("ERR_4091"), product names, IDs. BM25 — classic keyword search with term weighting — hits those exactly, but understands no synonyms. Hybrid runs both searches in parallel and fuses the rankings, usually via Reciprocal Rank Fusion (RRF): each hit earns 1/(k+rank) from every list, and the sum is the fusion score. Robust because RRF only compares ranks, not incompatible scores.

Re-ranking: cross-encoder vs. bi-encoder

The first search is fast but coarse. A re-ranker re-sorts the top-k candidates (say top 50):

  • Bi-encoder (embedding search): question and document are each mapped to their own vector, cosine distance between them. Fast enough for millions of documents — but the pair is never directly compared.
  • Cross-encoder: question + document go into the network together → direct relevance score. Much more accurate, but O(k) forward passes → only viable for ~50–100 candidates. Examples: Cohere Rerank, bge-reranker.

The pattern: buy recall from bi-encoders/BM25, buy precision from a cross-encoder.

Query transformation: HyDE, multi-query

  • Multi-query: the model rephrases the question 3–5 times (synonyms, perspectives) → run all variants, deduplicate results. Catches what one phrasing misses.
  • HyDE (Hypothetical Document Embeddings): the model first writes a fictional answer, then searches using that answer's embedding. The trick: candidate answers resemble each other more than question ↔ document — "answer-to-answer search".
  • Simpler: rewrite/condense questions (resolve chat history: "and she?" → "How old is Anna?").

Evaluating retrieval: Recall@k

Without measurement, every chunking debate is faith. The core metric is Recall@k — of all chunks containing the gold answer, how many made it into the top-k? For that you need a small eval set (~20–100 question/gold-chunk pairs), then change one thing at a time: chunk size, hybrid on/off, add a re-ranker. Complementary metrics: MRR (rank of the first correct hit) and ultimately end-to-end answer quality (15) — good retrieval is necessary but not sufficient.

Why this helps me

  • Diagnosis instead of gut feeling: "wrong answer" → first ask: was the right chunk in context? (Measure Recall@k.)
  • Cheap lever: better chunking/re-ranking often beats (and costs less than) a bigger LLM.
  • Exact + semantic: hybrid search covers both failure modes.
  • Transferable: the same ideas apply to code search (agent context, 35/41), not just docs-RAG.
