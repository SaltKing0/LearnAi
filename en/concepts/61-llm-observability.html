61 · LLM Observability

Explain it to a 12-year-old Imagine you baked a cake and it came out burnt. You can only fix it next time if you know why it went wrong — was the oven too hot, did you forget the timer, was the recipe wrong? Observability is like keeping a diary while you bake: you write down the temperature, the time, the ingredients, and what happened at each step. When an LLM app misbehaves in the real world, you need that same diary to see exactly where things went sideways.

Intuition

A demo works once in front of you. A production system has to work for thousands of users, around the clock, and it will fail in ways you never saw in testing. LLMs make this worse: the same prompt can give different answers, calls cost real money, and a single user request can fan out into many model calls and tool calls. If you can't see what a request actually did, you're debugging blind.

Observability is the practice of making a running system inspectable: capturing what happened, when, how long it took, what it cost, and whether the output was good. It turns "the app is broken" into "the retrieval step returned empty context and the model hallucinated a confident answer."

What happens technically

Structured logging of prompts and responses

Log every prompt, model, parameters, response, token counts, and latency as structured records (JSON), not free-form text. This is the raw material every other observability feature builds on. Beware of privacy: prompts and responses can contain user data, so redact secrets and PII before storing.

Tracing one request across model + tool calls

A single user turn may trigger a chain: an orchestrator calls the model, the model asks for a tool, the tool runs (a search, a database query), its result goes back into a second model call. A trace captures this whole tree as one unit with parent/child spans, so you can see the end-to-end path and the timing of each hop. Tools like Langfuse, LangSmith, and OpenTelemetry (with LLM semantic conventions) give you this out of the box for most frameworks.

Tracking cost and latency per request

Each model call costs money and time, and both scale with token count. Compute and record cost per request (input + output tokens × price per model) and latency per span. This lets you spot runaway costs from a single prompt, compare models, and set budgets before a bug empties your account.

Prompt versioning

Treat prompts as versioned artifacts, not magic strings. Every change to a prompt is a new version you can compare against production data. If quality drops after a "small tweak," you can roll back to the last good version and see which change caused the regression.

Eval-in-production (guardrails)

Testing happens before release; observability continues after. Run lightweight evaluations on live traffic — LLM-as-judge scoring, safety checks, schema validation, refusal/hallucination heuristics — as guardrails. When a score drops below a threshold, alert and/or reroute the request. This closes the loop between offline evals and real-world behavior.

Why this helps me (as a code user)

You cannot improve what you do not measure. Observability is what turns a demo into a production system: it tells you which prompt is costing you money, which tool call is slow, which user request produced a bad answer, and which prompt change broke quality. Without it, every production bug is a guessing game and every cost spike is a surprise invoice. With it, you debug in minutes instead of days, and you can iterate on prompts and models with real evidence.
