62 · Streaming & Transport

Explain it to a 12-year-old When you ask a chat bot a question, it doesn't wait until it has written the whole answer. It types it to you live, word by word, like a friend who is writing you a text message and you can already read the beginning while they are still typing the rest. Streaming is how the computer hands you those words one by one over the internet instead of making you wait for the whole letter.

Intuition

A model doesn't produce an answer in one piece — it produces one token at a time (Concept 12). Streaming is simply not hiding that: instead of the server collecting the full answer and sending it once at the end, it pushes each token to your app the moment it is generated. The transport (SSE or WebSockets, Concept 03) is the pipe that carries those tokens from the model's loop to your UI as they happen.

The two things people actually feel: first-token latency (how long until the first character appears) and perceived speed (watching text type out feels far faster than a spinner, even if the total time is the same). Streaming turns "waiting" into "reading".

What happens technically

A non-streaming request is request → wait → one big response. A streaming request opens a persistent connection and the server writes data: {...} chunks down it as each token is decoded. The client accumulates the chunks into the visible text and re-renders (Concept 06).

flowchart LR U[Your app / UI] -->|1. POST request
stream: true| A[LLM API] A -->|2. open SSE / WebSocket| C[Connection open] A -->|3. token 1
data: {...}| U A -->|4. token 2
data: {...}| U A -->|5. token N ...| U A -->|6. [DONE]| U U -->|abort / cancel
close connection| A

The stream is literally the autoregressive loop of Concept 12 delivered incrementally: each data: event carries the next token, and the client just appends. Two transports dominate:

  • SSE (Server-Sent Events) — a one-way HTTP stream from server to client. Simple, works over plain HTTP, auto-reconnects, great for text streaming. This is what most LLM APIs use.
  • WebSockets — a full-duplex connection (both directions). Needed when the client must also send data mid-stream (e.g. voice, live edits) or when you want to reuse one connection for many messages.

Partial responses and tool-call accumulation: with tool calls (Concept 27), the streamed chunks often include a growing JSON object (the tool name, then its arguments piece by piece). You can't act on a half-written JSON string, so the client buffers the chunks and only parses/executes once the stream signals it's complete. Same principle as accumulating visible text — but for structured data.

Abort / cancel: because the connection stays open, the client can close it (an AbortController in the browser, closing the socket on the server). The model stops generating, you stop charging tokens, and the UI stops appending. Without abort, a user hitting "stop" would keep paying for tokens the model keeps producing into the void.

Why this helps me (as a code user)

  • Streaming is the difference between a spinner and a live-typing chat. The same API call with stream: true feels instantly responsive; without it, users stare at a loader.
  • First-token latency is the metric users judge you on. Streaming shows progress even when the full answer takes a while.
  • You control the pipe. Choosing SSE vs. WebSockets depends on whether you need two-way traffic; picking the right one avoids overbuilding.
  • Abort handling is a cost control. Cancelling a stream stops token burn — important for any chat UI.
  • Tool-call accumulation is where agents get tricky: you must buffer partial JSON and only execute when it's complete.
