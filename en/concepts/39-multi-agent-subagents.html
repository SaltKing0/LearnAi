39 · Multi-Agent & Subagents

Explain it to a 12-year-old Sometimes several cooks working in parallel help — but too many cooks spoil the broth. Multi-agent is only good when the tasks are truly independent and can be merged cleanly.

Intuition

A subagent is its own agent with its own context window, its own system prompt, and its own tools. It gets a clearly scoped subtask, works in isolation, and returns only a compressed summary to the main agent. That keeps the main context clean.

But: multi-agent pays off less often than you'd think. When a task needs a shared decision, is sequential, or has shared state, a single loop is better (“Don't build multi-agents” — Cognition).

What happens technically

When it's worth it (all must hold)

  • Parallelism: ≥2–3 genuinely independent work streams (e.g. several research topics).
  • Isolability: each subtask describable as self-contained (goal, output format, tools, clear boundary).
  • Controllable merging: the main agent (parent) as a clear integration point that merges results.

Patterns

  • Supervisor / Orchestrator-Workers: a lead agent plans, delegates, synthesizes.
  • Planner-Executor: a heavy planner creates milestones, a light executor runs them.
  • Context isolation: a subagent returns only ~1000–2000 tokens, details go to a sidecar file (which the parent never loads).
  • Limits: depth limit (subagents can't spawn their own) + concurrency limit prevent exponential token usage.

Why it helps me (as a code user)

  • Broad research/exploration without clogging the main context.
  • You recognize when multi-agent hurts (shared state, merge conflicts, error dominoes) — and say so.
  • You understand the cost: each subagent = its own tokens + repetition.
