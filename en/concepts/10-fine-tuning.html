10 · Fine-Tuning (LoRA / PEFT)

Explain it to a 12-year-old Instead of explaining everything to the model in the prompt every single time, you let it practice on examples — like in Concept 05, only much smaller and on one special topic. With LoRA you clip a small trailer onto the model that it learns, instead of rebuilding the whole model. Cheap, fast, swappable.

The basic principle (connection to 05)

It's the same training as in Concept 05 — lowering loss by adjusting weights — just on a small, targeted dataset instead of the huge pre-training run. The result: a model "specialized" in your format/tone/domain.

Full fine-tuning vs. PEFT / LoRA

  • Full fine-tuning — all weights are adjusted. Expensive (lots of memory/GPU), risks "catastrophic forgetting" (losing general knowledge).
  • LoRA (Low-Rank Adaptation) — the base model stays frozen. Only small extra matrices (adapters) are trained and added alongside. Tiny (MB instead of GB), fast, and you can swap adapters like expansion cards.
  • PEFT = umbrella term for "train only a small part" (LoRA is the best-known variant).

Demo: base model + LoRA adapter

Visualization: the big model stays the same (frozen). The LoRA adapter (green) sits on top — when "ON", behavior is influenced by it without changing the base model.

When fine-tuning is worth it — and when NOT

  • Worth it: fixed output format, specific tone/style, domain jargon, many recurring similar tasks (cuts prompt & token costs at high volume).
  • Not worth it: general tasks, little example data, or when a good prompt (07) or RAG (08) already suffices. Training = effort.

Why this is central for you as a code user

  • Your own models offline/self-hosted, without asking an API every time.
  • LoRA is small: you version only the adapter, not the 7B model.
  • Ecosystem: Hugging Face PEFT library, axolotl, the tools from our Concept 11 (Stage D).
  • Distinction: RAG = knowledge at runtime; fine-tuning = baking in behavior.
