63 · Vector Databases

Explain it to a 12-year-old Imagine a giant library where every book is filed by how close its meaning is to other books. "Dog" sits right next to "puppy" and "pet", but far away from "rocket". A vector database is that library: it stores each idea as a list of numbers (its embedding) and, when you ask a question, it quickly finds the shelves holding the ideas most similar to yours — without reading every book.

Intuition

Embeddings turn text (or images, audio) into lists of numbers where similar meaning means nearby numbers. But a normal database can't search "nearby numbers" well — it's built for exact matches like WHERE name = 'dog'. A vector database is the storage and index layer that makes nearest-neighbor search fast: given a query vector, find the K stored vectors closest to it, and return the text they came from.

This is the engine behind RAG and semantic search. The embedding model turns your documents into vectors once; the vector DB stores them; at query time it turns your question into a vector and returns the most similar stored chunks, which then get fed to the LLM.

What happens technically

A vector database stores two things per entry: the vector (the embedding) and metadata (source text, title, timestamps, tags — anything you want to filter on). On top of that sits an index that makes "find nearest neighbors" fast.

The naive way is a brute-force scan: compare the query against every vector (exact, but O(N) and slow at scale). Real systems use Approximate Nearest Neighbor (ANN) search, which trades a little accuracy (recall) for huge speed gains. Common ANN approaches:

  • HNSW (Hierarchical Navigable Small World) — builds a multi-layer graph where each node is a vector and edges connect nearby vectors. Search starts at the top (few, coarse nodes) and walks down to finer layers, greedily hopping to neighbors closer to the query. Fast and high-recall, but the graph lives in memory.
  • IVF (Inverted File Index) — clusters all vectors into groups (e.g. via k-means). A query is first matched to the few nearest clusters, then searched only inside those. Cheap, disk-friendly, good for very large collections.
  • Product Quantization (PQ) — compresses each vector into a short code so many more vectors fit in RAM, at the cost of recall. Often combined with IVF or HNSW (e.g. "IVF-PQ", "HNSW-PQ").

These methods sit on a spectrum: recall vs. speed vs. memory. More recall needs more memory or more compute; more speed sacrifices a bit of recall. Every index exposes parameters (e.g. HNSW's M and ef_search, IVF's nlist and nprobe) to tune that trade-off for your data size and latency budget.

Choosing a vector database

Real options differ mainly in where they run and how much you manage yourself:

OptionTypeStrengthsTrade-offs
pgvectorPostgres extensionLives inside a DB you may already run; SQL + vector in one placeFewer ANN index options; needs tuning at large scale
QdrantDedicated (Rust)Fast, rich filtering, good HNSW defaultsAnother service to run
MilvusDedicated (distributed)Scales to billions of vectors, many index typesHeavier to operate
ChromaEmbedded / localZero-setup, Python-native, great for prototypingNot built for huge scale
PineconeManaged cloudNo ops, scales automaticallyVendor lock-in, cost

The "right" choice depends on your scale and infrastructure: for a small RAG app that already uses Postgres, pgvector is often the least new machinery; for a prototype, Chroma; for a large production system, a dedicated engine like Qdrant or Milvus (or a managed one like Pinecone).

Why this helps me (as a code user)

As someone writing RAG code, you rarely implement ANN yourself — you pick a store and an index and configure them. That choice directly drives your app's cost (managed vs. self-hosted, memory footprint), latency (index speed and recall settings), and result quality (a badly-tuned index returns irrelevant chunks, which the LLM then faithfully turns into a bad answer). Knowing the trade-offs lets you tune ef_search or nprobe instead of guessing, and lets you pick the store that matches your scale instead of over- or under-provisioning.
