45 · Sampling & Decoding

Explain it like I'm 12 Imagine the model is a friend finishing the sentence "I love eating ___". It suggests: "pizza" (55%), "pasta" (20%), "apples" (10%), "banana bread" (2%) ... The model only gives you this list of probabilities. Sampling decides which word actually gets picked — do you always take the favorite (boring, predictable), or do you roll dice weighted by the probabilities (surprising, creative)? Temperature and top-p are the rules for how you roll those dice.

Intuition

A language model does not return text. For every possible token it returns a number: the logit. After softmax, that's a probability distribution over the whole vocabulary (~50,000–200,000 entries). Only the decoding step turns that into the one token that ends up in your output. That choice is why the same question can produce different answers twice — and why you can dial creativity vs. precision with a knob.

What happens technically

The pipeline per generated token:

raw scores] --> S[Softmax] T[Temperature] --> S S --> F[Filtering

  • Logits → unnormalized scores per vocabulary entry (can be any size).
  • Softmax → turns them into probabilities (all between 0 and 1, summing to 1).
  • Temperature → divides logits by T before softmax. T<1 sharpens the distribution (safer), T>1 flattens it (more creative/wild).
  • Greedy decoding → always take the most probable token. In principle deterministic, but repetitive and often worse.
  • Top-k → keep only the k most probable tokens, zero out the rest, renormalize.
  • Top-p / Nucleus → take the smallest set of tokens whose cumulative probability ≥ p (e.g. 0.9). Adaptive: few tokens when the model is confident, many when unsure.
  • Beam Search → track the b best partial sequences in parallel instead of one. Standard for translation, but often bland/generic for open-ended generation.
  • Repetition Penalty → penalize already-generated tokens (lower or divide their logits) to fight loops.

Is temperature 0 truly deterministic?

No — not via an API. At T=0 the server formally takes argmax, but:

  • GPU computation is non-deterministic: floating-point additions in different orders (batching!, parallel reductions) can create bit-level differences.
  • With two nearly tied tokens (e.g. 0.5001 vs. 0.4999) argmax flips depending on batch composition.
  • MoE models and provider-side routing (different datacenters, hardware) amplify this.
  • Plus caching, model versions hidden behind the same name, etc.

Rule of thumb: T=0 makes output largely stable, but never guaranteed identical. If you need real reproducibility: set a seed (where offered) + pin the model version — or self-host.

Why it helps me

  • I understand what temperature / top_p really do in API calls — and that you usually vary one strongly rather than cranking both at once.
  • "The model hallucinated" is sometimes just "wrong sampling settings": high temperature on factual tasks is self-sabotage.
  • A/B comparisons (same prompt, two models) are worthless with different settings — settings are part of the experiment.
  • Loops and repetition from local models? Repetition penalty is usually the lever, not the prompt.
