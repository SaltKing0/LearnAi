46 · KV-Cache & Inference Optimization

Explain it like I'm 12 Imagine reading a long letter out loud, word by word. Without a cache: for every new word you re-read the entire letter from the start so everything fits together. With a cache: you keep notes on what you've already read and only need to fit in the new word. The KV-cache is the model's notebook — that's why generation doesn't get slower and slower as the answer grows.

Intuition

Attention needs every new token to look at all previous tokens. Naively, that means: at token n you compute attention over n keys/values → O(n²) cumulative work per sequence. The trick: the K- and V-vectors of earlier tokens/layers never change retroactively. So store them once and only compute the new token. That's the KV-cache.

What happens technically

  • Prefill → the whole prompt goes through the network in one pass (parallelizable, GPU-friendly). This determines time to first token (TTFT).
  • Decode → afterwards, tokens come out one at a time; each step is a forward pass with a single new token plus cache reads. This determines time per output token (TPOT). Decode is usually memory-bound: the cache must be read, not computed.

Memory footprint rule of thumb

bytes ≈ 2 (K+V) × n_layers × n_kv_heads × head_dim × seq_len × batch × bytes_per_number

Example: Llama-3-8B (32 layers, 8 KV heads of dim 128, FP16): 2 × 32 × 8 × 128 × 4096 tokens × 2 bytes ≈ 512 MB per sequence. At large contexts the cache eats more VRAM than the weights — hence PagedAttention in vLLM, GQA/MQA, and quantizing the cache too.

Prompt caching is closely related: providers store the KV-cache of a long, recurring prefix (system prompt, document) server-side. Follow-up calls only pay for the new part — lower TTFT and lower cost (e.g. Anthropic/OpenAI prompt caching). It only works up to the first divergent token.

Throughput vs. latency: heavy batching maximizes tokens/second per GPU but lengthens individual requests' wait times (queueing). Serving stacks tune this trade-off explicitly.

Why it helps me

  • I understand why long prompts dominate TTFT and long answers dominate TPOT — and where optimization targets each.
  • "Full context window = expensive" has a concrete cause: quadratic prefill and linearly growing cache.
  • Use prompt caching deliberately: stable system prompt + variable content at the end → saves real money and time.
  • With local serving I know why vLLM/Ollama differ sharply under parallel load (continuous batching).
