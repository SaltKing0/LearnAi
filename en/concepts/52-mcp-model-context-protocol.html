52 · MCP (Model Context Protocol)

Explain it to a 12-year-old Until now, every model↔tool connection needed its own custom cable: 10 tools = 10 different plugs. MCP is like USB-C for AI — one standard plug. If you offer a tool once as an MCP server, any MCP-capable model/client can use it. And vice versa: one client automatically understands all MCP servers.

What is MCP?

An open standard (from Anthropic, late 2024) for connecting AI applications to external context: tools, data, prompts. Before MCP, every app built its own function-calling integrations (Concept 29) — MCP unifies that into a client-server protocol.

flowchart LR A[Host · e.g. Claude Desktop, IDE] -->|MCP client| S1[Server: Files] A -->|MCP client| S2[Server: GitHub] A -->|MCP client| S3[Server: DB] S1 --- T1[Tools · Resources · Prompts] S2 --- T2[Tools · Resources · Prompts] S3 --- T3[Tools · Resources · Prompts]

One host can connect several MCP servers in parallel — each server exposes tools, resources, and prompt templates.

The three server primitives

  • Tools — functions the model may call ("read file", "create PR"). This is MCP's equivalent of function calling.
  • Resources — data the client can read/attach (files, DB rows). Context, not actions.
  • Prompts — ready-made prompt templates the server offers (e.g. "review this PR").

Why this is central for you as a code user

  • Build once, use everywhere: your MCP server works in Claude Desktop, IDEs, agent frameworks — no per-app reimplementation.
  • Less glue code: instead of 20 hand-written function definitions you consume ready-made servers (GitHub, Slack, Postgres …).
  • But: MCP doesn't solve the security questions — prompt injection via tool results (Concept 26) and sandboxing (Concept 40) remain your responsibility.
