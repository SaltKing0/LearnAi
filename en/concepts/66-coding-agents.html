66 · Coding Agents

Explain it to a 12-year-old Imagine a helper who can read your code, run it, and fix it — but instead of guessing, they check their own work. They make a change, run the tests, see one fails, read why, fix it, and run again — until all tests pass. That's a coding agent: an AI that writes, tests, and repairs code in a loop, using the test results as the truth about whether it got it right.

Intuition

A coding agent is an agent loop (23) specialized for software: instead of generic tools it gets code tools — read a file, grep the codebase, run the tests, edit a file — and instead of answering a question it produces a working change. The loop is: plan → act (read/grep/edit/run) → observe (test output) → adjust → repeat until the task is done. The key difference from a plain chat answer is that the agent can verify its own output by running it.

What happens technically

A coding agent (Claude Code, Codex, Cursor's agent mode) is a model wrapped in a harness that exposes code-specific tools (21) and keeps a working directory. Each loop iteration looks like this:

1. Plan: "add a --json flag to the CLI"
2. Act:   read_file("cli.py")   → understand current structure
3. Act:   grep("--json")        → check nothing already exists
4. Act:   edit("cli.py", ...)   → write the change
5. Act:   run("pytest")         → observe the test output
6. Observe: one test fails      → read the failure, fix, run again
7. Repeat until all tests pass  → done

Three ideas make this work:

  • The test harness is the ground truth (44): the agent doesn't trust its own judgment about "looks right" — it runs the tests and reads the verdict. The tests decide whether the work is done.
  • Self-healing: run → see failure → read the error → fix → run again. The failure message is feedback, not a dead end. Most coding agents spend most of their steps in this fix loop, not in the initial write.
  • REPL-driven development: the agent runs a snippet, reads the output, and iterates — a conversational version of the classic read–eval–print loop. Quick experiments against the live code replace long stretches of reasoning.

Under the hood each tool call is a function call (27) the model selects; the harness runs it, captures stdout/exit codes, and feeds the result back as the next observation. The model never executes code itself — the harness does, and the model only reads the transcript (21).

Why this helps me (as a code user)

  • This is a major real-world use case: coding agents are the most widely deployed form of agents today. Understanding the loop means you understand what the hype is actually doing under the hood.
  • You use the loop, not magic: to get good results you give the agent a clear task, a test to satisfy, and let it iterate. You're not "talking to a coder" — you're steering a loop.
  • You know what to check: because the test harness is the ground truth, the quality of your tests determines the quality of the agent's work. Weak tests → confident wrong code. This raises the value of writing good tests.
  • You can debug it: when a coding agent fails, the failure lives in the loop — a wrong tool call, a test that doesn't exist, an edit that didn't land. Knowing the pattern (23, 21) lets you find the weak link instead of staring at the output.
  • Architecture awareness: whether it replans, how much context it keeps, and which tools it trusts are the same design choices as any agent (60) — now you can judge tools by them.
