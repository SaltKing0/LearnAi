44 · Data Quality & Datasets

Explain it to a 12-year-old If you learn cooking from a cookbook that's half wrong, you'll never cook really well — no matter how long you practice. Models are the same: they get exactly as good (or bad) as the data they learn from. 1000 clean examples beat 100,000 garbage ones.

Why data is the real bottleneck

  • "Garbage in, garbage out": bias, errors and outliers in the dataset land directly in model behavior (Concept 16).
  • Scaling laws say: more + better data → better model. But high-quality web text is finite; quality beats quantity.
  • Especially for fine-tuning: with 100–10k examples, the quality of each individual example dominates the outcome.

What "good data" means

CriterionQuestion
RepresentativenessDoes the set cover real usage (languages, cases, edge cases)?
CorrectnessAre labels/answers reliable? Who produced them — human or model?
Diversity without redundancyDifferent phrasings yes, duplicates no (overfitting risk).
BalanceNo class/topic dominates just because it happens to appear more often.
Dedupe & PIIDuplicates removed, personal data removed/anonymized.
LicenseAm I allowed to train on this? (Legally often more important than technically.)

A practical workflow

1. Collect     → raw data (logs, documents, curated sources)
2. Filter      → dedupe (hash/embedding), language filter, toxicity, length
3. Quality score → heuristic or LLM-as-judge (Concept 34)
4. Split       → train / validation / test — never mix them!
5. Train       → watch loss, detect overfitting via validation loss (05)
6. Error analysis → look at bad cases → add targeted data

The loop 6→2 is the crucial one: data curation is iterative, not a one-time job.

flowchart LR RAW[Raw data] --> F[Filter/dedupe] F --> S[Quality score
heuristic / judge] S -->|bad| BIN[Discard] S -->|good| TR[Train split] TR --> M[Training] --> EV[Evaluation] EV -->|error analysis| GAP[Gaps identified] GAP -->|targeted collection| RAW

Curation as a cycle: evaluation results feed back into the next round of data.

Well-known reference datasets (for learning/studying)

  • C4 / The Pile / FineWeb — large web corpora for pre-training.
  • OpenAssistant / UltraChat / Tülu — instruction/dialog data for SFT.
  • MMLU / GSM8K / HumanEval — evaluation benchmarks (Concepts 15/34), NOT training data!

Why this is central for you as a code user

  • Fine-tuning success = data work: 80% of the time goes into curation, not training (Concepts 10/25).
  • Evals need your own data: an eval set from your real cases beats any benchmark.
  • RAG also lives on data quality: badly scanned PDFs = badly retrieved chunks (Concepts 08/30).
  • Legal risks (license, privacy) sit at the data, not the model.
