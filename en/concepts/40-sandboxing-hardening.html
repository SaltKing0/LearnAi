40 · Sandboxing & Hardening

Explain it to a 12-year-old Dangerous experiments belong in the playground, not the living room. Sandboxing means: code you don't trust runs isolated — so a mistake can't wreck the whole system.

Intuition

An agent runs code that it (or a model) wrote — often unreliable or malicious. So that a bug or attack does no damage, such execution runs in a sandbox: an isolated area with limited rights, files, and network access.

What happens technically

1) Risk tiers (least privilege)

  • Read-only: read/grep — no write rights, little risk.
  • Writable root: write only to allowed directories (writable_roots).
  • Irreversible: delete/force-push/deploy — always human confirmation.

2) Isolation levels

  • Light (bwrap/Landlock/seccomp): namespace/syscall isolation, ~0 overhead — good for read-only and small builds.
  • Medium (Docker-rootless/Podman): container with read-only rootfs, non-root user, no docker.sock — good for builds/execution.
  • Heavy (gVisor/microVM): own kernel — only for highly sensitive code.

3) Network & credentials

Outbound via allowlist (only allowed domains, better: SNI filtering at a proxy); credentials never in the sandbox context (e.g. Git token injected only on clone). Important: network AND filesystem isolation always together — otherwise a compromised process exfiltrates secrets.

Why it helps me (as a code user)

  • You can let agents run code autonomously without risking the machine.
  • You understand the security blast radius: sandbox per session = one bug hits only that session.
  • “Fail closed”: if the sandbox doesn't start, abort hard — never run unprotected.
