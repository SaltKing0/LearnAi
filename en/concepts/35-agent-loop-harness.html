35 · Agent Loop & Harness

Explain it to a 12-year-old An agent is like a cook who keeps going back to the fridge: he thinks, grabs an ingredient (a tool result), thinks again, grabs the next — until the dish is done. That “going back again and again” is the agent loop; the kitchen that makes it possible is the harness.

Intuition

A plain chat model answers once. An agent doesn't — it runs in a loop: think → call a tool → look at the result → think again. That way it can read files, run code, search the web, and then continue. The key point: it's the same loop repeating — nothing magical.

The harness is the wrapper program around the model: it builds the prompt, calls the API, runs tools, manages context, and decides when to stop. The model itself only “thinks one step.” Worth knowing: a good agent needs both — a good model AND a good harness.

What happens technically

while (model wants to keep going) {
  1. send:   context + system prompt + available tools
  2. infer:  model answers (text OR a tool call)
  3. if tool call:
       - execute the tool (e.g. read_file, bash, web_search)
       - append the result to the context
       - jump back to 1
  4. else:   done → emit the answer
}

Two things professionals watch for:

  • Context grows with each step. Every loop step is a new API call that re-sends the whole history. Long agent runs get expensive and slow — that's the O(n²) problem (see concept 36).
  • The harness must be able to abort. A stuck agent (rate limit, endless loop, wrong tool) needs a clean interrupt: an abort signal, keep partial output, never run a tool twice.

Why it helps me (as a code user)

  • You see where you steer: system prompt, tool list, context limit, interrupt — all that belongs to the harness, not the model.
  • You grasp why “good model” alone isn't enough — the loop and context management decide too.
  • You can estimate cost: each tool step = a new call = new tokens.
