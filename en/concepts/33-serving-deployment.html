33 · Serving & Production Deployment

Explain it to a 12-year-old Imagine you have a cook (the model) who bakes fantastic pizza. But he bakes in your kitchen (your laptop) and only for you. Serving is like opening a restaurant: the cook works in the kitchen, but 100 people can order at the same time, and everyone gets their pizza in 5 minutes. Serving makes the model scalable.

Why serving is different from inference

Single inference (one prompt → one answer) is easy. But what if 1000 users send a request at once? What if a request has 10,000 tokens? What if the model must be reloaded without downtime?

Core concepts

  • Batching → process several requests together → higher throughput
  • Continuous batching → requests that finish leave, new ones come in → no GPU idle time
  • KV-cache → cache the key-value cache for attention → less computation
  • Quantization → compress the model → less memory (see Concept 31)
  • Model parallelism → distribute the model across several GPUs
  • Tensor parallelism → each layer on a different GPU

Monitoring & observability

  • Latency → time to first token (TTFT), time per output token (TPOT)
  • Throughput → tokens/second, requests/minute
  • GPU utilization → VRAM usage, GPU utilization
  • Queue depth → how many requests are waiting?
  • Error rate → timeout, OOM, failed generations
