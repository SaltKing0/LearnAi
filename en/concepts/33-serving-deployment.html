33 · Serving & Production Deployment

Explain it to a 12-year-old Stell dir du hast einen Koch (das Modell) der fantastische Pizza backt. Aber er backt in deiner Küche (deinem Laptop) und nur für dich. Serving ist wie ein Restaurant aufmachen: Der Koch arbeitet in der Küche, aber 100 Leute können gleichzeitig bestellen, und alle bekommen ihre Pizza in 5 Minuten. Serving macht das Modell skalierbar.

Warum Serving anders ist als Inference

Einzelne Inference (ein Prompt → eine Antwort) ist einfach. Aber was wenn 1000 User gleichzeitig einen Request senden? What wenn ein Request aus 10.000 Tokens besteht? What wenn das Modell neu geladen werden muss ohne Downtime?

Kern-Concepte

  • Batching → Mehrere Requests zusammen verarbeiten → höherer Durchsatz
  • Continuous Batching → Requests die fertig sind raus, neue rein → keine GPU-Leerläufe
  • KV-Cache → Key-Value-Cache für Attention zwischenspeichern → weniger Berechnung
  • Quantisierung → Modell komprimieren → weniger Speicher (siehe Concept 31)
  • Model Parallelism → Modell auf mehrere GPUs verteilen
  • Tensor Parallelism → Jeder Layer auf eine andere GPU

Monitoring & Observability

  • Latency → Time to First Token (TTFT), Time per Output Token (TPOT)
  • Throughput → Tokens/Second, Requests/Minute
  • GPU-Auslastung → VRAM-Verbrauch, GPU-Utilization
  • Queue-Depth → Wie viele Requests warten?
  • Error-Rate → Timeout, OOM, fehlgeschlagene Generierungen
