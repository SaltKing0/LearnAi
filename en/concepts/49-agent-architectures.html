49 · Agent Architectures

Explain it to a 12-year-old Two ways to tackle a big homework assignment: The improviser takes one step, looks at what came out, takes the next — adjusting along the way. The planner first writes down the whole outline and then works through it. Both reach the goal, but depending on the task, one or the other is faster and more careful. That's exactly how ReAct and Plan-and-Execute are built.

Intuition

An agent (09) is a loop: Think → Act → Observe. But how you structure that loop is a design decision with real consequences for cost, robustness, and error rates. The two basic patterns are ReAct and Plan-and-Execute; everything beyond them (multi-agent, orchestrators) builds on top.

ReAct: think → act → observe

ReAct (Reason + Act) has the model alternate between reasoning ("Thought"), calling a tool ("Action"), and reading the result ("Observation") in every step — until it produces the final answer. No fixed plan; the strategy emerges step by step from the observations.

Step 1: Thought "First I need the price of X"
        Action: search("price of X")   Observation: "$12"
Step 2: Thought "Now compare with Y"
        Action: search("price of Y")   Observation: "$9"
Step 3: Thought "I have enough" → answer

Plan-and-Execute: plan first, then steps

Here the model generates a complete plan up front ("1. research, 2. compute, 3. write"), and an executor works through the steps — ideally without the planner having to re-read every intermediate result. When something surprising happens, it re-plans.

Rule of thumb: unclear what to do → ReAct; clear what to do, just long → Plan-and-Execute.

flowchart TD T[Task] --> R{Architecture} R -->|ReAct| L1[Pass: Thought] --> L2[Action] --> L3[Observation] --> L4{done?} L4 -->|no| L1 L4 -->|yes| D1[Answer] R -->|Plan & Execute| P1[Planner: full plan] --> W1[Worker executes step 1..n] --> P2{Plan still valid?} P2 -->|surprise| P1 P2 -->|ok| D2[Result]

Both architectures share the same loop skeleton (35) — they differ only in when planning happens.

Multi-agent patterns in brief: orchestrator/worker

Instead of one do-it-all agent, an orchestrator splits the task among specialized workers (39): "you research, you implement, you test", then aggregates and decides. Upsides: smaller contexts per agent, parallel execution, clear responsibilities. Downsides: coordination overhead, errors can hide between agents. For small tasks a single agent is almost always simpler and cheaper.

Key point: no framework replaces understanding the loop. If you know how ReAct works, you can rewrite any of these from scratch in ~100 lines if you have to.

Agent evals: how do you measure whether an agent is good?

  • Task success rate: fraction of solved tasks across a set of test cases — the core metric. Requires defining "solved" (tests pass, file correct …).
  • Steps & cost: how many model calls/tools/tokens until success? An agent with the same success rate at half the cost is better.
  • Trajectory evaluation: was the path sensible? (needless detours, files deleted then recreated, hallucinated tool calls). Done manually or via LLM-as-judge over the transcript.
  • Related: classic metrics (15), but lifted to the task level instead of token level; robustness against prompt injection (26) belongs on the scorecard too.

Why this helps me

  • Deliberate choice instead of default: I can decide whether my use case needs a ReAct, plan-first, or multi-agent profile.
  • Cost control: Plan-and-Execute saves real model calls on long tasks.
  • Measurability: without success rate + cost per task, agent building is pure vibes.
  • Framework independence: frameworks come and go; the loop stays.
