02 · System Architecture & Design

Explain it to a 12-year-old A monolith is one giant house where every room is connected and everyone shares one kitchen. Microservices are separate little houses that talk to each other by phone. "Architecture" is deciding how to split a big program into parts so it's easy to build, change, and fix — without everything breaking at once.

Intuition

Architecture is how you divide a system into pieces and how those pieces talk. The right split makes each part small enough to understand, replaceable, and independently scalable. The wrong split turns every change into a risky cross-cutting edit. There is no single best answer — only trade-offs between speed of development, cost, scalability, and operational complexity.

Design patterns

SOLID is a checklist for keeping code changeable:

  • Single Responsibility — a class has one job
  • Open/Closed — open for extension, closed for modification
  • Liskov Substitution — subtypes usable where their base is
  • Interface Segregation — small, focused interfaces
  • Dependency Inversion — depend on abstractions, not concretions

GoF patterns (Gang of Four) are reusable solutions to recurring problems. The ones you'll actually meet: Factory (create objects without naming the class), Singleton (one shared instance — e.g. a config or a DB pool), Observer (many listeners react to an event — the basis of event-driven systems and reactive UI), Strategy (swap algorithms at runtime — e.g. choosing a model or a retry policy).

Why this helps me (as an AI/code user)

  • Agent harnesses are systems: the model↔tool↔memory loop is an architecture — where the loop lives (harness vs. model) is a design decision (35).
  • RAG services: retrieval, ranking, and generation are natural service boundaries (8, 30).
  • Event-driven fits agents: tool results and streaming tokens are events; observers and message buses show up in real harness code.
  • Reading codebases: recognizing patterns (factory, observer, strategy) makes unfamiliar code familiar fast.
